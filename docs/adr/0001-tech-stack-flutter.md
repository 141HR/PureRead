# ADR-0001：选择 Flutter 作为 Windows + Android 跨端技术栈

- **状态**：已采纳
- **日期**：2026-11-24
- **关联文档**：[项目章程](./../00-charter.md) | [ADR-0002：统一 BookProvider 架构](./0002-unified-book-provider.md)

---

## 1. 背景与决策驱动因素

本项目需要构建一款同时覆盖 **Windows 桌面端** 与 **Android 移动端** 的网文及本地阅读器，且作为个人开源项目优先追求“一套代码覆盖双端、快速落地与长期可维护”。需求中最核心的差异化目标在于**极致阅读体验**：

1. **像素级中文排版控制**：需要精准实现两端对齐、行尾标点避头尾、中英文/数字混排微间距、自定义本地字体与纸纹主题。
2. **高刷跟手翻页动画**：移动端需要支持覆盖、平移、仿真卷页等 60/120fps 跟手交互；桌面端需要支持双栏仿真布局与窗口实时缩放重排。
3. **跨端渲染一致性**：Windows 与 Android 两端排版计算逻辑与视觉呈现必须高度一致，且能共享同一套业务状态与本地数据层。

---

## 2. 备选方案对比

| 维度 | Flutter (Dart) | Tauri 2 (Web 前端 + Rust) | KMP + Compose Multiplatform (Kotlin) | React Native / Electron |
| :--- | :--- | :--- | :--- | :--- |
| **Win + Android 一套代码成熟度** | ⭐⭐⭐⭐⭐ 双端官方一级支持，社区跨端应用案例丰富 | ⭐⭐⭐ 桌面端极佳，Android 支持自 2.0 引入但移动端生态仍较新 | ⭐⭐⭐⭐ Android 原生质感强，Windows 桌面端生态与打包体验稍弱 | ⭐⭐ RN 的 Windows 生态薄弱；Electron 不支持 Android |
| **自研分页与中文排版能力** | ⭐⭐⭐⭐⭐ 自绘渲染引擎，可用 `TextPainter` + `CustomPainter` 完全掌控分页与字距 | ⭐⭐⭐ 受限于 WebView2 与 Android WebView 差异，CSS 分页与跟手翻页较难对齐 | ⭐⭐⭐⭐ 可基于 Skiko 自绘，但现成中文排版与跨端资料少于 Flutter | ⭐⭐ DOM/原生视图混排难以实现双端统一像素级分页 |
| **系统能力扩展（音量键/本地文件/JS 引擎）** | ⭐⭐⭐⭐ 需为 Android 音量键、QuickJS 等编写或集成轻量插件 / FFI | ⭐⭐⭐⭐⭐ Rust 生态抓取解析极强，但移动端系统交互仍需桥接 | ⭐⭐⭐⭐⭐ 极易参考原版 Legado Kotlin 代码与原生能力 | ⭐⭐⭐ 双端桥接维护割裂 |
| **单人研发效率与资料丰富度** | ⭐⭐⭐⭐⭐ 热重载、单一语言栈、中文资料和组件库极为充足 | ⭐⭐⭐⭐ 前端快但需同时维护 TS + Rust 两套技术栈 | ⭐⭐⭐ 需熟悉 Kotlin Multiplatform 工具链 | ⭐⭐⭐ 无法兼顾双端 |

---

## 3. 最终决策

选择 **Flutter（当前基线 `3.47.7` / Dart `3.13.5`）** 作为唯一 UI 与核心应用框架，用于构建 Windows 与 Android 双端客户端：

1. **排版引擎层**：基于 Dart 纯逻辑与 Flutter `TextPainter` / `CustomPainter` 自研分页排版引擎，结合 `Isolate` 在后台线程预计算上一章尾、当前章与下一章头的页布局缓存，确保翻页阶段渲染线程只做轻量绘制。
2. **原生扩展边界**：通过极薄的平台适配层（Platform Channel / 成熟插件）封装平台特有能力——例如 Android 端的音量键拦截、屏幕常亮、全面屏安全区；Windows 端的窗口快捷键、无边框/沉浸模式、鼠标滚轮事件与系统字体目录读取。
3. **高性能原生互操作预留**：保留通过 **Dart FFI** 接入 C/C++（如 QuickJS 引擎）或未来引入 Rust 高性能解析模块的能力，核心领域接口不绑定特定底层实现。

## 4. 权衡与缓解措施

| 已知短板 / 风险 | 缓解措施 |
| :--- | :--- |
| **书源内嵌 `<js>` 执行能力**：Dart 本身不自带 JavaScript 运行时 | 通过独立 `JsRuntime` 接口封装嵌入式 QuickJS（如 `flutter_js` 或基于 Dart FFI 的 QuickJS 绑定），并限制单次脚本超时与内存配额，避免阻塞 UI 线程。 |
| **大文本计算与 UI 掉帧风险**：在主线程扫描 30MB TXT 或重排大章节会卡顿 | 所有大文件扫描、编码识别、正则净化与章节分页计算强制下沉至 `Isolate` 后台工作池；UI 层只消费不可变的 `PageLayout` 数据快照。 |
| **双端交互差异**：桌面键鼠宽屏与手机单手触控交互完全不同 | UI 视图层按交互模型拆分布局壳（自适应 Shell），共享同一套阅读内核与状态控制器，避免把移动端弹窗硬搬到桌面端。 |
